## 1. Схема карточки

| Поле | Тип | Правила |
|---|---|---|
| `id` | string | Уникален во всём хранилище. Неизменяем после создания. |
| `title` | string | Перед проверкой и сохранением обрезаются пробелы по краям (`str.strip()`). Длина после trim от 1 до 100 символов (`len()` в Python, т.е. в символах Unicode). Хранится уже обрезанным. |
| `description` | string | Любой текст, может быть пустым. Если поле не передано, сохраняется `""`. Пробелы не обрезаются, текст хранится как есть **[РК-1]**. |
| `status` | string | Ровно одно из трёх значений: `"новая"`, `"в работе"`, `"готово"`. Сравнение точное, с учётом регистра, после trim по краям **[РК-2]**. |

- **Статус по умолчанию.** При создании через API/UI сервер всегда ставит `"новая"`. Поле `status` в теле запроса на создание игнорируется (SPEC: «Создание со статусом новая»).
- **`id` при создании через UI/API.** Генерирует сервер, клиент `id` не передаёт **[РК-3]**. Формат: `C` и номер из 4 цифр с ведущими нулями (`C0001`, `C0002`, …). Следующий номер = максимальный номер среди существующих `id` вида `C\d+` плюс 1. Если такой `id` уже занят, номер увеличивается, пока не найдётся свободный. Префикс `C` выбран, чтобы не пересекаться с `T…` из CSV-файлов.
- **`id` при импорте CSV.** Берётся из файла после trim. Пустой `id` даёт ошибку строки **[РК-4]**.
- Удаления нет (SPEC: «Удаление не требуется»).

Пример объекта карточки в JSON (одна и та же форма в API и в файле хранения):
```json
{"id": "T001", "title": "Проверить скан", "description": "Первые три страницы", "status": "новая"}
```

## 2. Хранение

- **Формат.** Один JSON-файл в UTF-8:
  ```json
  {"tasks": [ {"id": "...", "title": "...", "description": "...", "status": "..."} ]}
  ```
  Порядок в массиве — порядок добавления. При обновлении карточка остаётся на своём месте **[РК-5]**. Запись выполняется с `ensure_ascii=False, indent=2`.
- **Путь по умолчанию:** `data/tasks.json`. Путь считается от каталога `submissions/zekayessss/SA09/`, а не от текущего каталога (вычисляется как `Path(__file__).resolve().parent.parent / "data" / "tasks.json"`) **[РК-6]**.
- **Переопределение пути:** аргумент `--data PATH`. Относительный путь разрешается от текущего рабочего каталога.
- **Атомарность.** Каждое изменение (создание, редактирование, импорт целиком) записывается так: временный файл в том же каталоге (`tasks.json.tmp`), затем `flush` + `os.fsync`, затем `os.replace(tmp, path)`. Импорт сохраняется одной записью после обработки всех строк **[РК-7]**.
- **Файла нет.** Хранилище считается пустым (`tasks = []`). Файл и родительский каталог (`mkdir(parents=True, exist_ok=True)`) создаются при первой записи. Чистое хранилище для reviewer: несуществующий путь `--data`.
- **Файл повреждён** (невалидный JSON или нет ключа `tasks`). Сервер не стартует, печатает в stderr `Ошибка: файл данных <path> повреждён: <причина>` и завершается с кодом 1. Файл не перезаписывается **[РК-8]**.
- Сервер однопоточный (`http.server.HTTPServer`), поэтому одновременных записей нет **[РК-9]**.

## 3. HTTP API

Общие правила:
- Все JSON-ответы идут с заголовком `Content-Type: application/json; charset=utf-8`, сериализация `ensure_ascii=False`.
- Ошибка всегда имеет вид `{"error": "<текст на русском>"}` **[РК-10]**.
- Неизвестный путь: `404 {"error": "Не найдено"}`. Неподдерживаемый метод на известном пути: `405 {"error": "Метод не поддерживается"}`.
- Тело JSON, которое не разбирается или не является объектом: `400 {"error": "Тело запроса должно быть JSON-объектом"}`.
- Поле не того типа (например, `title` не строка): `400 {"error": "Поле <имя> должно быть строкой"}`.

Тексты ошибок валидации полей (общие для API и импорта):

| Код | Текст |
|---|---|
| E_TITLE_EMPTY | `Название не может быть пустым` |
| E_TITLE_LONG | `Название длиннее 100 символов` |
| E_STATUS | `Недопустимый статус «<значение>»: разрешены «новая», «в работе», «готово»` |
| E_ID_EMPTY | `Не указан id` |
| E_COLUMNS | `Ожидается 4 поля, получено <N>` |

### 3.1 `GET /` — страница
Отдаёт `app/static/index.html` (`text/html; charset=utf-8`).

### 3.2 `GET /static/<file>` — статика
Отдаёт файлы из `app/static/` (`index.html`, `app.js`, `style.css`) с подходящим `Content-Type`. Пути с `..` или с подкаталогами: `404 {"error": "Не найдено"}`. В HTML подключать как `/static/app.js` и `/static/style.css`.

### 3.3 `GET /api/tasks` — список, поиск, фильтр
- Параметры query (оба необязательны, объединяются по И):
  - `q` — подстрока `title` без учёта регистра (`q.strip().casefold() in title.casefold()`). Пустой или отсутствующий `q` не фильтрует.
  - `status` — точное значение одного из трёх статусов. Пустой или отсутствующий не фильтрует.
- Порядок — порядок хранения.
- `200`:
  ```json
  {"tasks": [{"id": "T001", "title": "Проверить скан", "description": "Первые три страницы", "status": "новая"}]}
  ```
- `400` (недопустимый `status`): `{"error": "Недопустимый статус «архив»: разрешены «новая», «в работе», «готово»"}`

### 3.4 `POST /api/tasks` — создание
- Тело: `{"title": "Проверить скан", "description": "Первые три страницы"}`. `description` необязательно. `status` и `id` игнорируются.
- `201`:
  ```json
  {"task": {"id": "C0001", "title": "Проверить скан", "description": "Первые три страницы", "status": "новая"}}
  ```
- `400`: `{"error": "Название не может быть пустым"}` (в том числе для `"   "` и для отсутствующего `title`), `{"error": "Название длиннее 100 символов"}`. При ошибке ничего не сохраняется.

### 3.5 `PATCH /api/tasks/<id>` — редактирование
- `<id>` передаётся URL-кодированным, сервер декодирует через `urllib.parse.unquote`.
- Тело: любое непустое подмножество `{"title": "...", "description": "...", "status": "..."}`. Неизвестные поля и `id` игнорируются. Отсутствующие поля не меняются.
- Пример: `{"title": "Проверить PDF", "status": "готово"}`
- `200`:
  ```json
  {"task": {"id": "C0001", "title": "Проверить PDF", "description": "Первые три страницы", "status": "готово"}}
  ```
- `400`: тексты E_TITLE_EMPTY / E_TITLE_LONG / E_STATUS; если нет ни одного из трёх полей, то `{"error": "Нет полей для изменения"}`. Изменение применяется целиком или не применяется совсем.
- `404`: `{"error": "Заявка с id «X999» не найдена"}`

### 3.6 `POST /api/import` — импорт CSV
- Тело: сырые байты CSV-файла (`Content-Type: text/csv`). UI отправляет `fetch('/api/import', {method: 'POST', body: file})` **[РК-11]**.
- `200` возвращается, даже если все строки плохие:
  ```json
  {
    "accepted": [{"line": 2, "id": "T003", "action": "created"}],
    "errors": [
      {"line": 3, "id": "T004", "error": "Название не может быть пустым"},
      {"line": 4, "id": "T005", "error": "Недопустимый статус «архив»: разрешены «новая», «в работе», «готово»"}
    ],
    "created": 1,
    "updated": 0
  }
  ```
  `action` принимает значения `"created"` или `"updated"`. `id` в ошибке — значение из файла после trim, может быть `""`.
- `400` (ошибка файла целиком, ничего не сохраняется):
  - `{"error": "Файл не в кодировке UTF-8"}`
  - `{"error": "Файл пуст"}`
  - `{"error": "Неверный заголовок: ожидается id,title,description,status"}`

### 3.7 `GET /api/export` — экспорт CSV
- `200`, `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="tasks.csv"`. Тело описано в разделе 5.
- Экспортирует все записи, параметры `q`/`status` не учитываются **[РК-12]** (#39(4): «экспорт всех записей»).

## 4. Импорт CSV

- **Кодировка.** UTF-8, декодирование через `bytes.decode("utf-8-sig")`, так что BOM допустим и отбрасывается. Ошибка декодирования: 400 `Файл не в кодировке UTF-8`.
- **Разбор:** `csv.reader(io.StringIO(text, newline=""))`. Разделитель `,`, кавычки `"` по стандарту CSV, поля с переводами строк внутри кавычек поддерживаются.
- **Заголовок обязателен.** Первая запись после trim каждого поля должна быть ровно `["id","title","description","status"]` в этом порядке. Иначе 400 `Неверный заголовок…`. Если записей нет совсем: 400 `Файл пуст`.
- **Нумерация строк.** `enumerate(reader, start=1)`: заголовок = 1, следующая запись = 2 и т.д. Полностью пустые строки (`reader` отдаёт `[]`) пропускаются без ошибки, но номер расходуют. Запись с многострочным полем в кавычках считается одной строкой **[РК-13]**. На входных файлах это совпадает с номерами строк в редакторе.
- **Проверки строки по порядку (сообщается первая найденная ошибка) [РК-14]:**
  1. Число полей ≠ 4: `Ожидается 4 поля, получено <N>`
  2. `id.strip()` пуст: `Не указан id`
  3. `title.strip()` пуст: `Название не может быть пустым`
  4. `len(title.strip()) > 100`: `Название длиннее 100 символов`
  5. `status.strip()` не входит в три статуса: `Недопустимый статус «<status.strip()>»: разрешены «новая», «в работе», «готово»`
- **Статус в CSV обязателен и проверяется.** Пустой статус — ошибка E_STATUS (значение `«»`), «новая» по умолчанию не подставляется **[РК-15]**.
- **Обновление по существующему `id`.** Если `id` уже есть в хранилище, `title`, `description` и `status` заменяются значениями из строки (`action: "updated"`, позиция в списке сохраняется). Иначе запись добавляется в конец (`action: "created"`). Повтор того же `id` ниже в том же файле обновляет запись ещё раз, последняя строка выигрывает **[РК-16]**.
- **Плохие строки не мешают хорошим.** Каждая строка проверяется отдельно. Плохие попадают в `errors` и не меняют хранилище, хорошие применяются. В конце одна атомарная запись файла, если принята хотя бы одна строка.
- **Ответ** по форме из 3.6. `accepted` и `errors` идут в порядке строк файла. UI показывает их раздельно: «Принято: N (создано X, обновлено Y)» и список «Строка <line> (id <id>): <error>».

Ожидаемое на эталонных файлах:
- `import-valid.csv` в чистое хранилище: accepted T001 (строка 2), T002 (строка 3), обе `created`; ошибок нет.
- Тот же файл повторно: обе `updated`, всего записей 2.
- `import-mixed.csv`: accepted T003 (строка 2); errors: строка 3 (T004, `Название не может быть пустым`), строка 4 (T005, `Недопустимый статус «архив»: …`).

## 5. Экспорт CSV

- Заголовок: `id,title,description,status`.
- Строки идут в порядке хранения (тот же, что в `GET /api/tasks` без фильтров), все записи.
- Экранирование: `csv.writer(..., quoting=csv.QUOTE_MINIMAL, lineterminator="\n")`. Поля с `,`, `"` или переводом строки берутся в кавычки, `"` удваивается **[РК-17]**.
- Кодировка UTF-8 без BOM, как у входных файлов **[РК-18]**. Импорт принимает и BOM, и файл без него.
- Гарантия round-trip: экспорт и последующий импорт в чистый экземпляр дают те же `id`, `title`, `description`, `status`. Повторный импорт в тот же экземпляр даёт только `updated`, без копий.

## 6. Запуск

Из каталога `submissions/zekayessss/SA09/`:
```
python3 app/server.py [--port 8000] [--data data/tasks.json]
```
- Хост фиксирован: `127.0.0.1`.
- Порт по умолчанию `8000` **[РК-19]**.
- Флаги (`argparse`):
  - `--port INT` — порт.
  - `--data PATH` — путь к JSON-файлу данных (см. раздел 2).
- После старта сервер печатает `Сервер запущен: http://127.0.0.1:<port>/ (данные: <абсолютный путь>)`. Остановка через Ctrl+C, без трассировки.
- Тесты хранилища: `python3 -m unittest discover -s tests` из того же каталога.

Обязательные элементы UI (для ui-worker):

- форма создания (название, описание);
- редактирование названия, описания и статуса существующей карточки;
- выбор CSV-файла и кнопка импорта; результат показывает принятые отдельно от ошибок с номерами строк и причинами;

- отображение текста `error` из ответов API.

Пользовательские данные вставляются только через `textContent`, без `innerHTML` **[РК-20]**. После каждого изменения или импорта список перезапрашивается с текущими `q` и `status`.

## 8. Разделение файлов между исполнителями

| Исполнитель | Файлы (относительно `submissions/zekayessss/SA09/`) | Ответственность |
|---|---|---|
| storage-worker | `app/store.py`, `app/server.py`, `tests/test_store.py` | Валидация, хранение JSON (раздел 2), импорт и экспорт CSV (разделы 4–5), HTTP API и раздача статики (раздел 3), запуск (раздел 6), unit-тесты хранилища на эталонных CSV |
| ui-worker | только `app/static/index.html`, `app/static/app.js`, `app/static/style.css` | Страница из раздела 7; общается с сервером только через HTTP API раздела 3 |

- Точка стыка — только раздел 3: пути, методы, формы JSON, `{"error": ...}`, CSV-тело импорта, `/api/export`.
- ui-worker не трогает Python. storage-worker не трогает `app/static/`.
- `data/` создаётся во время работы и исполнителям не принадлежит. Инструкцию запуска и результаты сценариев ведёт координатор.
- Рекомендуемый интерфейс `app/store.py` (внутренний, для `server.py` и тестов) **[РК-21]**:

## Решения контракта (во входах не заданы)

1. **РК-1** `description` не обрезается и хранится как есть. Если не передано, сохраняется `""`.
2. **РК-2** Статус сравнивается точно, с учётом регистра, после trim по краям.
3. **РК-3** `id` при создании через UI генерирует сервер в формате `C0001`: максимальный номер `C…` плюс 1, с пропуском занятых.
4. **РК-4** Пустой `id` в CSV — ошибка строки `Не указан id`.
5. **РК-5** Порядок хранения и списка — порядок добавления. Обновление не меняет позицию.
6. **РК-6** Путь данных по умолчанию: `submissions/zekayessss/SA09/data/tasks.json`, от расположения кода, а не от текущего каталога.
7. **РК-7** Атомарная запись через временный файл, `fsync` и `os.replace`. Импорт пишется одной записью.
8. **РК-8** Повреждённый файл данных: сервер не стартует, код 1, файл не перезаписывается.
9. **РК-9** Сервер однопоточный (`HTTPServer`).
10. **РК-10** Единый формат ошибки `{"error": "..."}` и конкретные русские тексты из таблицы раздела 3 и из 3.5/3.6.
11. **РК-11** Импорт: тело `POST /api/import` — сырые байты файла, а не multipart. Ошибки уровня файла дают 400, ошибки строк — 200 с отчётом.
12. **РК-12** Экспорт всегда выгружает все записи и игнорирует фильтры.
13. **РК-13** Номер строки — номер записи `csv.reader` (`start=1`). Пустые строки пропускаются, но номер расходуют. Многострочное поле — одна строка.
14. **РК-14** Порядок проверок строки CSV; сообщается первая ошибка. Неверное число полей — ошибка строки, а не файла.
15. **РК-15** Пустой статус в CSV — ошибка, «новая» не подставляется.
16. **РК-16** Повтор `id` в одном файле: последняя строка выигрывает (вторая считается `updated`).
17. **РК-17** Экспорт: `QUOTE_MINIMAL`, перевод строки `\n`.
18. **РК-18** Экспорт в UTF-8 без BOM.
19. **РК-19** Порт по умолчанию `8000`, флаги `--port` и `--data`. Хост не настраивается.
20. **РК-20** UI вставляет пользовательские данные только через `textContent`.
21. **РК-21** Внутренний интерфейс `TaskStore` и классы исключений в `app/store.py`.
22. Порядок проверки: I1 и I2 выполняются на отдельном чистом хранилище, потому что после C1–C2 поиск «ПРОВЕРИТЬ» дал бы две записи. Для I3 файл с изменённой T001 готовит проверяющий: во входах его нет.
